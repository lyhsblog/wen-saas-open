# 前端模块接入

本篇讲一个业务前端模块如何挂进 wen-saas 前端工程：monorepo 里放在哪、manifest 怎么写、路由如何注册、菜单与套餐门禁由谁负责。配套的后端模块接入见[后端业务模块开发系列](../后端开发/01-业务模块工程结构.md)；页面里能复用哪些组件见[页面开发工具箱](./02-页面开发工具箱.md)。

## 一、monorepo 结构与模块的位置

```
wen-saas-frontend/            pnpm workspace
├── apps/                     三个可部署入口，独立构建、独立域名
│   ├── ops-web/              平台运营端
│   ├── tenant-web/           租户管理后台（业务模块的主战场）
│   └── h5/                   租户移动端（antd-mobile）
├── packages/                 共享基座包（@wen-saas/*）
│   ├── module-runtime/       模块 SPI：manifest 类型 + registry
│   ├── api-client/ auth/ permissions/ shared-ui/ design-system/ domain/ ...
└── modules/                  前端业务模块包
    └── base/                 底座模块（模块身份声明的最小样板）
```

一个业务模块的前端交付物由两部分组成：

1. **一份 manifest**：实现 `@wen-saas/module-runtime` 的 `BusinessModuleManifest`，声明模块身份与路由贡献。`code` / `name` / `version` 与后端模块保持一致。
2. **一组页面组件**：放在目标 app 的 `src/features/{module}/` 下（页面通常要引 app 内的 http / query 装配，故归属 app；`modules/` 下的包只承载与 app 无关的部分）。

`modules/base/src/manifest.ts` 是最小样板——只有 `code` / `name` / `version` / `description` 四个身份字段，路由由入口 app 注册时补上。

## 二、manifest 声明什么、不声明什么

类型定义在 `packages/module-runtime/src/manifest.ts`：

```ts
export type BusinessModuleManifest = {
  code: string;                 // 模块编码，与后端模块一致
  name: string;
  version: string;
  icon?: string;
  description?: string;
  dependsOn?: string[];         // 依赖的模块编码；registry 按拓扑序注册，缺失/成环报错
  alwaysOn?: boolean;           // true = 不按套餐门禁，对所有租户恒可达（见 §四）
  tenantRoutes?: RouteContribution[];   // 租户后台路由
  h5Routes?: RouteContribution[];       // H5 路由（h5 app 已接动态挂载，见文末「三端接入现状」）
  dictionaryGroups?: DictionaryContribution[];        // 预置字典分组
  notificationTemplates?: NotificationTemplateContribution[];
  importEntities?: ImportEntityContribution[];
};
```

路由贡献是核心：

```ts
export type RouteContribution = {
  path: string;        // 相对租户根的路径，如 '/crm-demo/customers'
  loader: () => Promise<{ default: ComponentType }>;   // 懒加载组件（React.lazy 等价）
  component?: LazyExoticComponent<ComponentType>;      // 已包好 lazy 时可直接给（与 loader 二选一）
  permission?: string; // 访问该路由所需权限点，如 'crm_demo.customer.view'
  workbenchActionUrl?: string; // 仅 h5Routes 用：对应工作台卡片的 actionUrl（PC 路由形），
                               // H5 工作台据此把命中卡片设为可点并导航到本路由
};
```

**manifest 刻意不声明的东西**（这是接入时最容易想错的地方）：

- **菜单不在 manifest 声明。** 导航菜单树的权威在后端数据库（`sys_menu`），登录后经 `GET /api/v1/me/capabilities` 的 `menus` 字段下发，后端已按当前用户权限 + 套餐过滤好，前端 `AppShell` 直接渲染。新模块要出现在侧栏，是在运营端的菜单管理里配置菜单项，不是改前端代码。
- **权限点不在 manifest 声明。** 权限点由后端模块的 `BusinessModuleDescriptor` 注册，前端只在路由与按钮上引用权限码字符串。
- **工作台入口不在 manifest 声明。** 租户工作台的"常用入口"从 `capabilities.menus` 拍平派生，业务卡片由后端工作台接口下发——模块菜单配好后自动出现，前端零代码。

所以对多数业务模块来说，manifest 有效载荷就是：`code` + `alwaysOn` 与否 + `tenantRoutes` 列表。

## 三、注册：registerModules 与路由挂载

入口 app 在构建期集中注册模块。以 tenant-web 为例（`apps/tenant-web/src/lib/modules.ts`）：

```ts
import { registerModules, type BusinessModuleManifest } from '@wen-saas/module-runtime';
import { baseManifest } from '@wen-saas/base-module';

const crmDemoManifest: BusinessModuleManifest = {
  code: 'crm_demo',
  name: '客户管理 Demo',
  version: '0.0.1',
  alwaysOn: false,          // 业务模块：按套餐门禁
  tenantRoutes: [
    {
      path: '/crm-demo/customers',
      loader: () =>
        import('../features/crmdemo/CustomersPage').then((m) => ({ default: m.CustomersPage })),
      permission: 'crm_demo.customer.view_manage',   // 管理视图与个人视图（view）是两次独立授权
    },
  ],
};

export const moduleRegistry = registerModules([
  { ...baseManifest, alwaysOn: true, tenantRoutes: [/* 底座页面路由 */] },
  crmDemoManifest,
]);
```

`registerModules`（`packages/module-runtime/src/registry.ts`）在注册时做三件事，全部**失败即抛错**，问题在构建/启动期暴露：

- 重复 `code` 报错；
- `dependsOn` 指向未注册的模块报错；
- 依赖成环报错；通过后按拓扑序排列（被依赖者在前）。

路由挂载由 `apps/tenant-web/src/lib/page-routes.tsx` 完成：`moduleRegistry.getTenantRoutes()` 返回**全量**路由（不按能力过滤），每条路由被包装成稳定的页面 element——

```
PackageGate(非 alwaysOn 模块，未开通 → 「模块未开通」占位页)
  └─ PermissionGate(route.permission，无权限 → 403 占位页)
       └─ Suspense(懒加载页面组件)
```

（PackageGate 在最外层：未开通模块直打 URL 先撞「模块未开通」占位页，而不是 403。）

新模块加完 manifest 后**不需要碰 router 代码**，路由自动注入。

## 四、套餐门禁：alwaysOn 与 enabledModules 的关系

前端把模块分成两类：

| 类别 | `alwaysOn` | 例子 | 行为 |
|---|---|---|---|
| 底座/通用模块 | `true` | 工作台、字典、文件中心、平台工单 | 菜单与路由对所有租户恒可达，不看套餐 |
| 业务模块 | `false`（缺省） | `crm_demo` | 仅 `capabilities.enabledModules` 含其 code 的租户可达 |

背后的约定：后端 capabilities 的 `enabledModules` **只包含套餐内的业务模块**，底座能力与通用工具（后端不注册 API 前缀、不参与套餐拦截的模块）永远不在这个列表里——所以这类模块必须置 `alwaysOn: true`，否则会被误判为"未开通"。

门禁是三层一致的：

1. **菜单层**：后端下发 `capabilities.menus` 时已滤掉未开通模块的菜单项，入口不可见；
2. **路由层**：直打 URL 时 `PackageGate` 按 `enabledModules` 判定，未开通渲染"模块未开通"占位页；套餐到期只读态由 `PackageGate` 的 `readonlyFallback` 属性控制（`@wen-saas/permissions` 包）——`true` 时到期仍渲染页面（配合 `useIsReadonly()` 灰掉写按钮），`false`（默认）整体替换为到期提示；路由层统一开着 `readonlyFallback`，业务页面无需自行处理；
3. **API 层**：后端网关级拦截器对未开通模块的 API 前缀真拦截——前端门禁只是体验，不是安全边界。

## 五、接入清单（新模块照此走）

1. 后端模块就绪：`BusinessModuleDescriptor` 已注册（权限点、菜单在运营端配置、API 前缀）。
2. 在目标 app 建 `src/features/{module}/`，写页面组件（组件与数据层写法见[页面开发工具箱](./02-页面开发工具箱.md)）。
3. 写 manifest：`code` 对齐后端，业务模块不设 `alwaysOn`，每条 `tenantRoutes` 带懒加载 `loader` 与 `permission`。
4. 在 `apps/tenant-web/src/lib/modules.ts` 的 `registerModules([...])` 里追加。
5. 验证三件事：有权限 + 已开通 → 页面可达；无权限直打 URL → 403 占位页；未开通租户直打 URL → "模块未开通"占位页。

三端接入现状：tenant-web 走上述完整链路；ops-web 是纯运营侧应用，菜单同样吃后端下发、不走 module-runtime；**h5 app 同样走 manifest 动态挂载**——模块清单在 `apps/h5/src/lib/modules.ts`，`h5Routes` 由 `lib/module-routes.tsx` 生成路由并统一包 登录守卫 + 套餐门禁 + 权限门禁（与 tenant-web 的 `page-routes.tsx` 同构，占位页换 antd-mobile）。给业务模块加 H5 页只需两步：建 `apps/h5/src/features/{module}/` 页面组件 + 在 h5 的 `modules.ts` 追加 manifest，不碰 router 与工作台代码。

仓内示例是 crm_demo 的「我的客户」页（`features/crmdemo/MyCustomersPage.tsx`）：路由 `/crm_demo/my-customers` 与后端 `h5Pages()` 声明对齐（租户由子域名区分，路由不带租户前缀）（模块 code 前缀，启动期校验命名空间；注意 H5 路由用下划线形，与 PC 的 `/crm-demo/*` 短横形不同），复用共享包里与 PC 同一份 API 工厂。入口在工作台业务卡片——卡片 `actionUrl` 是 PC 路由，H5 路由在 manifest 里用 `workbenchActionUrl` 声明对应关系，工作台据此派生"命中才可点击"的跳转映射，不再手工维护映射表。
