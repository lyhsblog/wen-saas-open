# 需求书：设备报修

本文档是 [快速开始（非程序员）](<../快速开始(非程序员).md>)的配套需求书：交给 AI 编程助手，让它按此在本项目中开发一个小而完整的业务模块。需求刻意压在底座接入的最小闭环上，适合作为第一次上手体验。

## 交付要求（给承接开发的 AI）

- 模块编码用 `repair_demo`，与真实业务模块区隔；
- 只依赖 `open-docs/` 文档与仓内代码，不要臆造底座没有的机制；优先使用底座现成能力，而不是自己造轮子；
- 范围刻意很小：遵守文中「明确不做」的红线，不要自行扩充功能，也不要照搬样板里本需求用不到的能力（导入导出、自定义字段、开放 API 等都不需要）；
- 每完成一个部分自行验证（启动通过、接口可调、页面可用）再继续。

## 需求正文

**背景**：办公室设备坏了——打印机卡纸、会议室灯不亮、空调漏水——现在都是在群里喊一声，行政看到就修，看不到就石沉大海。修没修、谁在修、什么时候修好的，没人说得清。

**角色**：

- **员工**：提交报修，跟进自己报修的进展；
- **行政管理员**：查看全部报修，处理并标记完成。

**报修单**只有两个状态：提交后为「待处理」，管理员处理后为「已完成」。不需要审批，也不需要中间状态。

字段：位置、问题描述、状态（待处理 / 已完成）、提交人、提交时间、处理备注、完成时间。

**功能需求**：

1. **我要报修**（员工）：填写位置（如"3 楼会议室"）和问题描述，提交报修单；能看到自己提交过的报修单和每单的进展（状态、处理备注）。员工只能看到自己提交的单子。
2. **报修处理**（管理员）：全部报修单列表，可按状态筛选、按问题描述搜索；处理完填写处理备注、标记完成，系统记下完成时间。
3. **工作台**：管理员在工作台看到「待处理报修」数量；员工看到自己「未完成报修」数量。
4. **权限**：管理员能管全部报修单，员工直接访问管理页面要被拒绝。

**明确不做**（超出本期范围，请勿实现）：站内通知、MQ、`@Auditable`操作审计、图片/附件上传、自定义字段、Excel 导入导出、手机 H5 页面、定时提醒、与第三方系统对接（开放 API / Webhook）、审批流、维修工程师派单。

## 附：能力覆盖对照表（验收用）

每条需求都有底座能力的自然落点。左边是需求，中间是应落到的底座能力，右边是验证动作——开发完成后可以照着逐条检查。若 AI 用了别的实现路径但效果达标，也算过。

| 需求 | 应落到的底座能力 | 验证动作 |
|---|---|---|
| 模块本体 | `@BusinessModule` 描述符 + 模块独立 Flyway 版本线（`db/migration/repair_demo/`，表名 `repair_demo_` 前缀，含 `tenant_id`） | 后端启动日志无校验报错；表已建 |
| 页面 + 菜单 | tenant-web manifest 注册 + `sys_menu` 菜单（种子脚本或运营端菜单管理页录入，模块自己的迁移脚本里不 INSERT） | 租户端导航出现「设备报修」，能提交、能处理 |
| 权限双视图 | 权限点拆「我的 / 管理」两次独立授权，Controller 挂 `@RequirePermission`；「只看我的」按提交人过滤是普通业务条件 | 普通成员登录只见自己提交的单子；直接打开管理页 URL 得 403 |
| 工作台卡片 | 描述符 `dashboardCards()` 声明 + 卡片 Provider（照 `module-crm_demo` 的 dashboard 包样例） | 管理员与员工登录后，工作台各见对应数字卡片 |
| 开箱即用 | `packages()` 预置套餐包 | 运营端套餐列表出现 `repair_demo` 预置包；未授予套餐的租户访问模块接口得 402 |

**结果怎么看**：AI 一次跑通，说明文档 + 样板足够自解释；中途卡住时留意它是"找不到机制"还是"用错机制"——前者多半是文档缺口（欢迎到公开仓提 issue），后者把对应的接入指南篇目喂给它通常就能纠偏。重新编译、重启服务这类命令行操作应由 AI 按 [Docker全容器运行](Docker全容器运行.md) 自行完成，不要求人来执行；人负责的只是在浏览器里按上表的验证动作逐条走查。

体验完如果不想保留产物：删除 `wen-saas-boot/modules/module-repair_demo` 与 `app/pom.xml` 里对应依赖、前端对应 feature 目录与 manifest 登记项，并清掉数据库里该模块的表和 `flyway_history_repair_demo`。
