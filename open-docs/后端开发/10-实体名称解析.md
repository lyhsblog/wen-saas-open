# 实体名称解析

底座把「id → 展示名」正向翻译与「关键字 → 候选实例」反向搜索统一为一个名称解析框架。业务模块给自己的实体注册一个**名称源 Bean**（一行链式调用），以下能力全部自动接通：

- **类型显示名**——字段管理页对象列表等处的中文 label（如「客户」）；
- **自定义字段 REF**——对象出现在 REF 字段的"关联对象"候选里，REF 值翻出 `__label`（见 [自定义字段接入](05-自定义字段接入.md)）；
- **操作日志**——实体 code 成为 `@Auditable.objectType` 的合法取值，审计页可按对象搜索筛选（见 [操作日志接入](08-操作日志接入.md)）；
- **选对象下拉**——前端「选人 / 选部门 / 选关联实例」类组件的搜索接口；
- **响应 DTO 翻名**——`@TransField` 声明式回填外键名称，替代每个 service 手写 `selectBatchIds → Map → getOrDefault`；
- **数据变更日志翻名**——`@DisplayRef` 标注外键列后，变更明细自动把 id 译成名称。

## 一、核心概念

两个接口都在 `core-api` 的 `com.wensaas.core.api.namesource` 包：

| 接口 | 方向 | 用途 |
|---|---|---|
| `NameLookup` | 正向：id → 展示名 | 批量翻译外键列、REF `__label`、审计渲染 |
| `NameSearch` | 反向：关键字 → 候选实例 | 「选对象」下拉 / 弹窗搜索（可选能力） |

每个名称源有一个全局唯一的**实体类型 code**（`NameLookup.entityType()`）：

- 底座内建实体的 code 收在常量类 `EntityTypes`（同包）：`sys.user`（成员）、`sys.dept`（部门）、`sys.role`（角色）、`sys.package`（套餐）、`sys.tenant`（租户）；
- **业务实体的 code 自行定义**，落在模块命名空间内（如 `crm_demo.customer`），**不登记进 `EntityTypes`**；接入自定义字段的对象必须与 `CustomFieldObjectDef.code` / `@CustomFieldExtension.objectCode` 用同一个 code。

## 二、注册：`NameSourceFactory` 一行构建

对 id / name / code 列规整的实体，注入 `NameSourceFactory`（`com.wensaas.core.api.namesource.NameSourceFactory`）声明一个 `@Bean` 即可，纯 core-api 依赖：

```java
@Configuration(proxyBeanMethods = false)
public class CrmDemoNameSourceConfiguration {

    @Bean
    public NameLookup crmDemoCustomerNameSource(NameSourceFactory factory) {
        return factory
                .source(CrmDemoModule.OBJECT_CUSTOMER, "客户", true,   // code、类型中文名、租户端可搜
                        CrmDemoCustomer.class, CrmDemoCustomer::getId)
                .primary(CrmDemoCustomer::getName, "名称", MatchMode.PREFIX)   // 主显字段（必填）
                .secondary(CrmDemoCustomer::getCode, "编码", MatchMode.EXACT)  // 辅助字段（可选，最多一个）
                .build();
    }
}
```

- `primary` / `secondary` 各带 `(getter, 中文名, 匹配模式)`：中文名驱动前端提示文案与弹窗列头；`MatchMode.PREFIX` 前缀匹配（名称类）、`MatchMode.EXACT` 精确匹配（编号 / code 类）；
- 单据类"编号即主体"的实体，把编号设为 `primary` 并加 `.render(RenderMode.BOTH)` 同时展示两个字段；
- 构建出的实例**同时实现 `NameLookup` 与 `NameSearch`**，内置租户线安全的查询改写，不必手写搜索 SQL；
- 需要 join、加密列等值、跨库的实体，绕过工厂直接实现 `NameLookup`（及可选的 `NameSearch`）接口。

## 三、两个开关

| 开关 | 含义 | 何时设 false |
|---|---|---|
| `tenantSearchable`（`source(...)` 第三参） | 允许在**租户上下文**内反向搜索 | platform-only / 跨租户实体（如 `sys.tenant`），防越权跨租户泄露 |
| `referenceable`（builder 方法，默认 `true`） | 是「可被别处引用的数据记录实体」 | 权限 / 配置构件（如角色）——能被搜索（审计按对象筛选要用），但不该被业务记录关联 |

两者正交：自定义字段 REF 的"关联对象"候选 = `tenantSearchable && referenceable` 都为 true 的类型。

## 四、响应 DTO 翻名：`@TransField`

响应里"存 id、展示名"的字段不必手写批量查询，在 DTO 的派生字段上声明引用来源，service 注入底座的 `TransFill` 接口（`core-api` 的 `namesource` 包）、构造完响应调一次 `fill(dto)`——根对象也可以直接传 List / 数组，整批一次取数：

```java
@Getter @Setter
public class CustomerView {
    private Long ownerId;

    @TransField(type = EntityTypes.SYS_USER, ref = "ownerId")
    private String ownerName;      // fill 后 = ownerId 对应成员的展示名
}
```

按 `type` 分组批量取数、原地回填，翻不出的（已删除 / 无值）保持原值不抛错，前端按 id 兜底。注意事项在 `@TransField` 的 javadoc 里写全了，最容易踩的两条：**嵌套对象里的 `@TransField` 必须在持有字段上标 `@TransDescend`**（漏标静默不回填）；宿主 DTO 须是可变 POJO（反射写回，record 写不进）。`type` 不限于实体 code——注册 `ValueTransform` Bean 可做任意 code → 文案类转换。

## 五、数据变更日志翻名：`@DisplayRef`

实体外键字段标 `@DisplayRef`，数据变更明细里该列的 id 自动译成名称：

```java
@DisplayRef(value = EntityTypes.SYS_USER, label = "负责人")
private Long ownerUserId;   // 变更日志显示 负责人=张三，而非裸 id
```

底座启动期扫描所有 `@TableName` 实体收集声明，建立「(表, 列) → 实体类型」注册表，业务只标注解、不用额外登记。

## 六、接入检查清单

1. 定义实体类型 code（模块命名空间内；接入自定义字段的对象与 `objectCode` 复用同一 code）；
2. `NameSourceFactory` 注册名称源 Bean，选好 `tenantSearchable` / `referenceable`；
3. 需要出现在审计里的实体：`@Auditable.objectType` 直接填这个 code（启动期校验，未注册即 fail-fast）；
4. 响应 DTO 的"id + 名称"字段对改用 `@TransField` + 注入 `TransFill` 调 `fill`；
5. 外键列标 `@DisplayRef`，让数据变更日志可读。
