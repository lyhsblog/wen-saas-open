# 权限与菜单接入

一个请求打到业务模块端点，会依次穿过四道闸门：**认证**（过滤器，未登录 401）→ **套餐门禁**（过滤器，按模块拦 402/403）→ **功能权限**（`@RequirePermission` 切面，无权限 403）→ **数据权限**（`@DataPermission` + MyBatis-Plus 拦截器，行级过滤）。前两道底座全自动，业务模块只需要做三件事：声明权限点、给 Controller 挂注解、把菜单录进 `sys_menu`。

## 一、声明功能权限点

权限点通过模块入口 `BusinessModuleDescriptor.permissions()` 声明，定义体是 `com.wensaas.core.api.spi.def.PermissionDef`（record）：

```java
@BusinessModule
public class CrmDemoModule implements BusinessModuleDescriptor {

    @Override
    public List<PermissionDef> permissions() {
        return List.of(
                new PermissionDef("crm_demo.customer.view", "客户 · 查看",
                        "「我的客户」视图与客户详情；客户数据范围以本权限点配置"),
                new PermissionDef("crm_demo.customer.view_manage", "客户 · 管理视图",
                        "「客户管理」全量列表、按负责人筛选与导出；需配合「客户 · 查看」一并授予"),
                new PermissionDef("crm_demo.customer.edit", "客户 · 编辑", "新增 / 编辑 / 删除客户、推进状态"));
    }
}
```

- **命名规范**：`{module}.{menu}.{action}`，点号分隔，全局唯一，必须以模块 code 开头（命名空间启动期强校验），如 `crm_demo.customer.view`；
- **粒度建议按"视图/操作"拆**：同一实体的「个人视图」与「管理视图」是两次独立授权（如上例 view / view_manage），不要用一个 view 混管——否则普通成员与管理者的菜单/入口无法差异化；
- 启动期由 `BusinessModuleRegistrar` 收集进内存 `PermissionRegistry`，角色管理页据此渲染可勾选的权限树；
- 注意：`@RequirePermission` 写了未声明的 code **拦截照样生效**，但该权限点不会出现在角色配置页，等于谁也授不了——声明与注解务必配套。

## 二、@RequirePermission：功能权限校验

注解定义在 `com.wensaas.core.api.auth.permission.RequirePermission`，可放 Controller **方法或类**上（方法优先于类）：

```java
@RequirePermission("crm_demo.customer.edit")               // 单一权限
@RequirePermission(anyOf = {"crm_demo.customer.view",
                            "crm_demo.customer.edit"})     // 任一命中即放行（OR）
```

语义要点：

- `value` 与 `anyOf` 都是 **OR**（任一命中放行）；**没有 AND 组合**——需要多权限同时满足时拆成多个端点或在业务内自行判定；
- 校验由 `RequirePermissionAspect`（AOP）执行：**租户主管理员（tenantOwner）无条件放行**；两参数都为空的裸注解 = 只要求已登录；
- `@PublicEndpoint`（类或方法）标注的公开端点跳过认证，其余端点必带 `Authorization: Bearer <token>`。

### 401 与 403 的语义

| 状态 | 触发点 | 含义 |
|---|---|---|
| 401 | `AuthenticationFilter`（无 token / 会话失效，进不到 Controller）或切面发现登录上下文缺失 | 未认证，前端走静默刷新 / 重新登录 |
| 403 | 切面查库后权限未命中（`PermissionDeniedException.Code.FORBIDDEN`） | 已认证但无此功能权限，前端提示权限不足 |

两者统一返回 RFC 7807 `ProblemDetail`（`application/problem+json`），`code` 属性为 `NOT_AUTHENTICATED` / `FORBIDDEN`，由 `AuthRestExceptionAdvice` 映射——业务代码不要自己 catch 拼响应。

## 三、数据权限：data_scope 行级过滤

功能权限管"能不能调这个接口"，数据权限管"调了以后能看到哪些行"。范围值存在角色上（`sys_role_data_scope` 表），枚举 `DataScope`：

| 取值 | 语义 | 过滤方式 |
|---|---|---|
| `ALL` | 全部数据 | 不加条件 |
| `DEPT_AND_BELOW` | 本部门及以下 | `deptColumn IN (本部门 + 全部子孙部门)` |
| `DEPT_ONLY` | 仅本部门 | `deptColumn IN (直属部门)` |
| `SELF` | 仅本人 | `creatorColumn = 当前 userId` |

用户有多个角色时按**最宽松**合并（`ALL > DEPT_AND_BELOW > DEPT_ONLY > SELF`）。接入三步：

1. **声明参与表**：模块 `dataPermissionTables()` 返回 `DataPermissionTableDef(resource, resourceName, tableName, creatorColumn, deptColumn)`。`creatorColumn` 是 SELF 范围的过滤列（归属人语义的表传 `owner_id`，纯记录语义传 `created_by` / `creator_id`）；`deptColumn` 是部门范围的过滤列，传 `null` 则部门类范围下该表**保守不可见**（注入 `1=0`）：

```java
@Override
public List<DataPermissionTableDef> dataPermissionTables() {
    // 客户是可分配资源：行级归属按「负责人」口径（SELF=owner_id、DEPT=owner_dept_id），创建人不是业务归属
    return List.of(new DataPermissionTableDef(
            "crm_demo.customer", "客户", "crm_demo_customer", "owner_id", "owner_dept_id"));
}
```

2. **查询端点挂注解**：`@DataPermission("crm_demo.customer.view")`（value 是权限点 code，可选 `tables` 限定只过滤某些物理表）。它与 `@RequirePermission` 独立共存、互不依赖。两条实践约定（crm_demo 即样板）：
   - **同一实体的多个读端点共用同一个锚点 action**：管理列表 `@RequirePermission(view_manage)`、详情 `@RequirePermission(view)`，但 `@DataPermission` 统一写 view——"能进哪个视图"由功能权限区分，"视图里能看到哪些行"只留一个范围旋钮，避免各视图分别配范围后出现"列表可见、详情打不开"的错位；
   - **业务条件已保证行归属的端点不必挂**：「我的客户」`GET /mine` 恒按 `owner_id = 当前用户` 查询，行集合本身就是行级最窄档（SELF），任何角色范围叠加都不会更窄——这类端点不挂 `@DataPermission`，省一次范围解析与 SQL 改写；
3. **写路径填好归属列**：insert 时业务代码自己把归属列（如 `owner_id` / `owner_dept_id`）填上，过滤才有依据。

过滤本身零代码：MyBatis-Plus 拦截器（`DataPermissionHandlerImpl`）在 SQL 改写期自动追加 WHERE，与租户隔离、自定义字段重写在同一条拦截器链上叠加。**主管理员同样跳过数据权限**。业务层的"只看我的"筛选（如 `?mine=true`）是普通业务条件，与数据权限正交，照常自己写。

## 四、菜单注册：sys_menu 是唯一权威

菜单树以 `sys_menu` 表为唯一权威——**纯平台表，无 tenant_id，全租户共用一棵树**，端与端靠 `scope` 区分（1=运营 / 2=租户 / 3=H5）。租户之间的差异不在树结构，而在"角色持有哪些权限码"：前端拉菜单时按当前用户权限过滤 `permission_code` 未命中的节点。

关键列：

| 列 | 语义 |
|---|---|
| `scope` | 端：1 运营 / 2 租户 / 3 H5 |
| `node_key` / `parent_key` | 稳定键与树父，`(scope, node_key)` 唯一 |
| `node_type` | 1=GROUP（分组容器）/ 2=PAGE（导航页，有 `path`）/ 3=ACTION（页面内动作码） |
| `label` / `icon` / `path` / `sort` | 显示名 / 图标 / 前端路由 / 同级排序 |
| `permission_code` | PAGE 的可见性门槛（为 null 的 PAGE 对所有人可见）、ACTION 的动作码；**与权限点相连的唯一纽带**；GROUP 恒 null |
| `source` / `status` | 来源（种子/后台新增）与启停 |

**菜单不走 SPI**，没有"模块声明菜单"的代码扩展点，业务模块的迁移脚本里也不要 INSERT `sys_menu`。两条正路：

- 开发期：在底座的菜单种子迁移脚本中为模块追加 GROUP / PAGE / ACTION 节点，`permission_code` 填模块 `permissions()` 声明的 code；
- 运行期：通过运营端「菜单管理」页录入（`source` 为后台新增，可删；种子节点只能停用）。

启动期有一致性校验（`MenuPermissionConsistencyValidator`）：菜单引用的 `permission_code` 若不在后端权威权限目录中，该节点被标 `dangling=true` 并打 ERROR（不阻断启动）；反之权限点无任何菜单引用则打 WARN。菜单码写错了启动日志会直接告诉你。

## 五、套餐门禁与权限的关系（一句话）

套餐门禁在 Servlet Filter 层（`PackageStatusWebFilter`）按 `apiPathPrefixes()` 反查模块、先于一切权限注解执行：租户未购买该模块返 402，套餐过期只读态下的写请求返 403——所以功能权限只需要回答"这个人有没有这个操作"，"这个租户买没买这个模块"永远不用业务代码操心。

## 六、当前用户上下文

鉴权链路使用自研 `com.wensaas.core.api.auth.user.UserContext`（ThreadLocal，过滤器注入）：

```java
UserPrincipal me = UserContext.require();   // 未认证抛 IllegalStateException；get() 返回 null
me.userId();  me.tenantId();  me.username();  me.realName();
me.tenantOwner();   // 是否租户主管理员（权限/数据权限全跳过）
me.mainDeptId();    // 主部门，写路径填 owner_dept_id 常用
```

异步 / MQ / 定时任务里 ThreadLocal 为空，需要用 `UserContext.runAs(principal, ...)` 显式注入（与 `TenantContext.runAs` 同理）。

## 七、接入检查清单

1. `permissions()` 声明权限点，code 用 `{module}.{menu}.{action}` 点分格式；
2. Controller 方法挂 `@RequirePermission`；多权限任一放行用 `anyOf`；
3. 需要行级过滤的表：`dataPermissionTables()` 声明 + 查询端点挂 `@DataPermission` + 写路径填 creator / dept 列；
4. 菜单进 `sys_menu`（种子脚本或菜单管理页），`permission_code` 与第 1 步声明的 code 对齐；
5. 启动应用，看日志有无 dangling 菜单告警；
6. 用主管理员和一个仅有部分权限的普通成员各测一遍：403、菜单裁剪、数据范围是否符合预期。
