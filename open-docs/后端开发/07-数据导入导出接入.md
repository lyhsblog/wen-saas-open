# 数据导入导出接入

底座提供两套对称的通用框架，业务模块只需注册少量 Bean 即可让自己的实体获得完整的导入 / 导出能力：

- **导入**：模板下载 → 上传并同步解析 + 全量预校验 → 预览确认 → 提交任务中心异步写库 → 结果（含失败明细 xlsx）下载。
- **导出**：列表页发起（携当前筛选）→ 按合规开关分流（直接执行 / 走审批）→ 任务中心异步流式生成 xlsx → 下载。

两者的执行运行时都复用任务中心：进度查询、SSE 推送、取消、结果下载统一走 `/api/v1/tasks/{id}/...`，同租户同 handler 串行，业务方不需要自己处理并发。

> 仓内可运行示例见 `module-crm_demo`：导入三件套 `CrmDemoModule.importEntities()/taskHandlers()` + `CrmDemoCustomerImportTaskHandler` + `CrmDemoCustomerImportValidationResolver`（含"字典/枚举列接受 code 或中文双写法"与"按手机/邮箱定位成员"两个常见校验模式，后者用 `UserQueryService.userByContact`——联系方式是加密列，等值定位必须走该接口而非自拼 SQL）；导出两件套 `CrmDemoModule.exportObjects()` + `CrmDemoCustomerExportProvider`（演示**自定义字段动态展开为导出列**、走"需审批"全链路）。前端入口见 `features/crmdemo/CustomersPage.tsx` 的 `ImportEntryButton`/`ExportEntryButton`。
>
> 导入执行 handler 若要调用依赖 `UserContext` 的业务 service：任务线程默认只有租户上下文，操作人经提交参数（`operatorId`）透传——覆写 `execute` 用 `UserContext.runAs` 包住 `super.execute(ctx)`（crm_demo handler 即此写法）。

## 一、导入侧：三个注册点

### 1. 声明导入实体（模板列定义）

在模块的 `BusinessModuleDescriptor.importEntities()` 返回 `ImportEntityDef`（`core-api` 的 `spi/def` 包）。字段定义即模板：底座据此生成模板 xlsx、按表头严格匹配解析上传文件、执行基础校验。

```java
@Override
public List<ImportEntityDef> importEntities() {
    return List.of(ImportEntityDef.of("crm_demo.customer", "客户", "crm_demo.task.import.customer", List.of(
            new ImportFieldDef("客户名称", "name", FieldType.STRING, true,
                    null, UniqueScope.IN_FILE, null, "示例客户"),
            new ImportFieldDef("联系电话", "phone", FieldType.STRING, false,
                    "PHONE", UniqueScope.NONE, null, "13800138000"),
            new ImportFieldDef("负责人部门", "deptName", FieldType.STRING, true,
                    null, UniqueScope.NONE,
                    new ReferenceDef("sys.dept", ReferenceMatch.BY_NAME, "部门", null), "销售部"))));
}
```

要点：

- `code` 按 `{module}.{entity}` 命名全局唯一；`taskHandlerCode` 绑定执行处理器（见第 3 步）。
- `ImportFieldDef` 的 `header` 是模板中文表头（严格匹配、不做自动列映射），`key` 是 handler / resolver 取值键；`format` 支持内置 token `PHONE` / `EMAIL`、日期模式或自定义正则；`example` 会预填进模板示例行。
- `UniqueScope.IN_DB` / `BOTH` 声明「与已有数据查重」、`ReferenceDef` 声明「关联对象须存在」——引擎按声明自动批量校验，业务方只需实现取数口（见第 2 步）。`ReferenceDef` 的 `label` 用于错误文案（「部门不存在: xx」），`inFileKey` 支持自引用实体的同文件前向声明（如部门导入「先建父再建子」：填 `"name"` 后，更早行该列声明过的值视为已存在）。
- `ImportEntityDef.of(...)` 使用默认行数上限 5000（`DEFAULT_ROW_LIMIT`）+ 需预览确认；有特殊需要用全参构造调 `rowLimit` / `needPreview`。
- 字段定义就是对外契约：改字段 = 改模板 = 客户需重新下载模板，改动要有版本意识。

### 2. 预校验钩子（可选）：`ImportValidationResolver`

必填 / 类型 / 格式 / 文件内唯一由底座引擎按声明自动校验。涉库校验实现 `ImportValidationResolver`（`core-api` 的 `imports` 包）并注册为 Bean，三个 default 方法按需覆写：

- **`existingDbValues(fieldKey, values)`**：`UniqueScope.IN_DB/BOTH` 字段的查重取数口——返回入参中已存在于 DB 的值，引擎自动给命中行回写 `DUPLICATE_IN_DB`（文案「{表头}已存在: {值}」）。实现内可先做等值变换（如确定性加密）再查。
- **`resolveReferences(field, values)`**：`ReferenceDef` 字段的关联匹配取数口——返回「值 → 目标 id」，`containsKey` 即存在，未命中行由引擎回写 `REFERENCE_NOT_FOUND`；无数值 id 的目标（如按 code 关联的字典分组）value 置 `null`（须用允许 null value 的 Map，别用 `Map.of`）。解析出的 id 映射会随校验产物透传执行处理器的 `prepare`，写入阶段可直接复用、免二次查询。
- **`validate(rows, sink)`**：声明表达不了的业务特有规则（枚举解析、按联系方式定位成员等），逐行判定后用 `sink.addError` 回写。

```java
public class CustomerImportValidationResolver implements ImportValidationResolver {

    @Override
    public String entityCode() {
        return "crm_demo.customer";   // 与 ImportEntityDef.code 一致，每实体一个
    }

    @Override
    public Map<String, Long> resolveReferences(ImportFieldDef field, Set<String> values) {
        // "deptName" 列的 ReferenceDef 取数：一次批量查，只返回命中的值→id
        Map<String, Long> all = deptQueryService.nameToId();
        Map<String, Long> hit = new HashMap<>();
        values.forEach(v -> { Long id = all.get(v); if (id != null) hit.put(v, id); });
        return hit;
    }
}
```

调用发生在请求线程内，租户 / 用户上下文已就绪可直接查库。取数口返回 `null` 表示未实现（引擎跳过该字段并记 warn，用于发现「声明了却没配取数」）；已实现取数口的实体对不相关字段返回空集合即可。任意行有错即禁止进入执行阶段，错误行在预览页与错误明细 xlsx 中可见。

与加密字段相关的 DB 唯一性（如账号 / 手机加密落库无法子串查询）**不要在预校验里重造**：交给执行期写入服务抛冲突异常兜底，失败行会自动进结果明细。

### 3. 执行处理器：`TaskHandler`

在 `BusinessModuleDescriptor.taskHandlers()` 声明 `new TaskHandlerDef("crm_demo.task.import.customer", CustomerImportTaskHandler.class)`，实现类注册为 Bean。执行阶段的标准模式（内置的部门 / 成员 / 字典导入即此骨架，参考实现见 `core-impl` 的 `com.wensaas.core.impl.imports.AbstractImportTaskHandler`）：

1. 从 `ctx.params()` 取 `fileId`，用 `FileService.readContent(fileId)` 重读原始文件并**重新解析 + 重校验**——天然抓住"解析到确认"之间产生的并发冲突；
2. `ctx.setTotal(n)` 声明总数（进度分母），随后逐行调用**本模块既有的写入服务**（复用唯一性 / 租户隔离 / 加密等约束，不要绕过服务层裸写表）；
3. 循环内：成功 `ctx.recordSuccess(1)`、失败捕获异常 `ctx.recordFailure(1)` 并收集明细，周期调 `ctx.updateProgress(percent, processed)` 与 `ctx.isCancelled()`（为 true 优雅退出）；
4. 收尾把失败明细写成 xlsx 落文件中心，`ctx.setResult(Map.of("total", t, "success", s, "failed", f, "fileId", 明细文件Id))`，前端经 `/api/v1/tasks/{id}/download` 获取。

注意：handler 是**单例 Bean，不同租户可能并发执行**，单次执行的中间态（如 name→id 映射）必须走局部变量传递，严禁存实例字段。

导入向导相关端点由底座统一提供（`/api/v1/imports/entities`、`/{entityCode}/template`、`/{entityCode}/parse`、`/sessions/{sessionId}/confirm` 等），业务模块无需写 Controller。

## 二、导出侧：两个 Bean

### 1. 声明审批治理对象：`ExportObjectContributor`（`core-api` 的 `compliance/spi` 包）

```java
@Component
public class CrmExportObjects implements ExportObjectContributor {
    @Override
    public List<ExportObjectDef> exportObjects() {
        // code 全局唯一；末位 defaultRequiresApproval：含敏感个人信息建议 true
        return List.of(new ExportObjectDef("crm_demo_customer", "客户列表", "crm_demo", true));
    }
}
```

这一步让导出对象出现在合规策略页的"是否需审批"开关上（页面在哪、审批怎么流转见下文"审批治理"节）。

### 2. 提供取数实现：`ExportDataProvider`（`core-api` 的 `exports/spi` 包）

```java
public class CrmCustomerExportProvider implements ExportDataProvider {

    @Override public String objectCode() { return "crm_demo_customer"; }   // 与 ExportObjectDef.code 一致

    @Override public String requiredPermission() { return "crm_demo.customer.view_manage"; }  // 复用管理视图权限点（能看全量列表才能导出）

    @Override public List<ExportColumn> columns() {
        return List.of(new ExportColumn("name", "客户名称"), new ExportColumn("owner", "负责人"));
    }

    @Override public long estimateCount(Map<String, String> filters) {
        return customerService.page(query(filters, 1, 1)).total();    // 仅作申请信息展示
    }

    @Override public void export(Map<String, String> filters, ExportSink sink) {
        int page = 1;
        while (!sink.stopped()) {                                     // 取消 / 触达行数上限时尽快返回
            var result = customerService.page(query(filters, page, 500));  // 分页拉取防 OOM
            result.items().forEach(c -> sink.row(Arrays.asList(c.name(), c.ownerName())));
            if (result.items().size() < 500) return;
            page++;
        }
    }
}
```

注册为 Bean 即完成接入，发起端点（`POST /api/v1/exports`）与任务执行由框架统一承担。`filters` 是 string→string 宽 map，键由 provider 与前端列表页自行约定，未知键忽略、注意向后兼容。

**权限与审批联动一句话**：发起时校验 `requiredPermission`（能看列表才能导列表）；若合规策略页开了该对象的审批开关，则申请必须填理由并等审批，审批通过后框架**以申请人身份**投任务执行——`export` 运行在申请人的用户上下文内，已注册数据权限的表自动按申请人数据范围过滤，审批只控制"能不能导"、不放大数据范围。因此取数直接复用列表页同一查询服务即可，数据权限 / 租户隔离 / 敏感字段掩码自动同口径。

### 3. 审批治理：合规策略页与流转（业务模块零代码参与）

**合规策略页**是租户端「系统管理 → 数据隐私与合规」页（路由 `/system/compliance`；菜单权限 `base.compliance.export.approve`，策略配置另需 `base.compliance.config`，主管理员恒可见）。管理员在这里按导出对象逐个开关"是否需审批"，并配置审批权限归属（仅主管理员 / 持"导出审批"权限的角色）与审批超时提醒。`defaultRequiresApproval` 只是**租户未单独配置时的回退值**：租户改过某对象的开关后即落覆盖记录，此后模块默认值对该对象不再生效；其余未改对象继续回退默认。

审批流转全部由底座承担，业务模块只声明 `ExportObjectDef`：

1. **发起**：业务列表页放任务中心的 `ExportEntryButton`（传 `objectCode` + `filters`），调 `POST /api/v1/exports`。对象开了审批时理由必填，申请落台账（`PENDING`）并站内信通知审批人；未开审批则直接建导出任务；
2. **审批**：审批人在任务中心「待审批」Tab 通过 / 拒绝（`/api/v1/base/compliance/export-requests/{id}/approve` / `/reject`，可填审批意见）；
3. **通过**：底座按申请时的参数快照、以申请人身份投递导出任务，申请人收站内信、在「导入导出」页看进度与下载；**拒绝**：不投任务，站内信告知申请人。

- [ ] 导入：`ImportEntityDef.code` = resolver 的 `entityCode()`；`taskHandlerCode` = `TaskHandlerDef.handlerCode` = handler 的 `handlerCode()`
- [ ] 导入：handler 写库全部委托本模块服务层；无实例字段持有执行状态；循环内查 `isCancelled()`
- [ ] 导出：`ExportObjectDef.code` == `ExportDataProvider.objectCode()`（不一致 → 策略页有开关但发起报错）
- [ ] 导出：`requiredPermission` 已在模块 `permissions()` 注册；`export` 分页拉取并在循环边界查 `sink.stopped()`
- [ ] 导出：敏感字段输出与列表回包同口径（掩码），不要在导出里放大敏感面
