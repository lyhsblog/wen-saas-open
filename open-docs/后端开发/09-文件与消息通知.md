# 文件与消息通知

业务模块存文件、发通知都不直接碰对象存储或消息队列，统一走 `core-api` 的两个门面：`FileService`（文件）与 `MessageService`（通知）。

## 一、文件：`FileService`

文件本体存对象存储后端，元数据（`sys_file`）永远在 PG。业务文件用 `visibility = BUSINESS_ONLY` + owner 三元组归属到业务对象，与用户可见的文件中心（`FILE_CENTER`）隔离。

### 服务端直传（≤100MB 小文件）

```java
FileUploadResult result = fileService.uploadDirect(new FileUploadRequest(
        "合同扫描件.pdf",              // fileName
        "application/pdf",            // mimeType，可空（按扩展名兜底）
        bytes.length,                 // sizeBytes
        new ByteArrayInputStream(bytes),
        FileVisibility.BUSINESS_ONLY, // 业务文件：仅业务详情页可见，文件中心不展示
        "crm_demo",                   // ownerModule：BUSINESS_ONLY 时必填
        "customer",                   // ownerRefType：业务对象类型
        customerId,                   // ownerRefId：业务对象 ID
        null));                       // folderPath：仅 FILE_CENTER 用
String fileId = result.fileId();      // 业务表里只存这个对外 ID
```

### 前端直传（大文件，不过后端带宽）

1. 业务后端调 `fileService.requestSignedUpload(new SignedUploadRequest(...))`（字段同上、无内容流），拿到 `SignedUploadUrl`（元数据已落库，状态 uploading）；
2. 前端拿 URL 直接 PUT 到对象存储；
3. 前端回调后，后端调 `fileService.confirmUpload(fileId)`——底座校验后端真实存在后置为 active。超时未确认的孤儿记录由定时任务清理。

### 下载与其它操作

- `signedDownloadUrl(fileId, Duration.ofMinutes(5))`：生成签名下载 URL（Redis 短缓存），客户端直连对象存储下载。
- `listByOwner(ownerModule, ownerRefType, ownerRefId)`：业务详情页列附件。
- `metadata(fileId)` / `delete(fileId)`：查元数据 / 软删（30 天后定时物理清理）。
- `readContent(fileId)`：服务端读全部字节，**仅限受信内部流程**（如任务重读源文件），只做租户隔离、不做用户级权限，大文件慎用。

### 下载权限：`FilePermissionChecker`

`BUSINESS_ONLY` 文件默认放行下载；业务对象有自己的访问控制（如客户按负责人隔离）时，为本模块注册一个 checker，签名下载时被回调：

```java
@Component
public class CrmFilePermissionChecker implements FilePermissionChecker {
    @Override public String ownerModule() { return "crm_demo"; }   // 与上传时的 ownerModule 一致
    @Override public boolean canDownload(FileMetadata file, Long currentUserId) {
        return customerService.canAccess(currentUserId, file.ownerRefId());
    }
}
```

仓内可运行示例：`module-crm_demo` 的 `CrmDemoFilePermissionChecker` + 前端 `CustomerAttachments`
组件——客户详情抽屉的附件区**零自建表**：上传 / 列表 / 下载 / 删除全部走通用 `/api/v1/files` 端点
（owner 三元组 `crm_demo / customer / 客户id`），业务表不存任何文件字段，checker 做「客户存在且未删」
校验（客户删除后附件即拒绝下载）。注意 checker 仅在下载 URL 缓存 miss 时被回调，缓存热的窗口内
（默认 ≤4 分钟）权限收紧不即时生效。

**存储后端配置一句话**：文件写到哪由 `sys_storage_config` 决定——平台默认一份、租户可自配（本地 / 阿里云 OSS / 腾讯云 COS 适配器），租户切换后端后历史文件仍按其原配置可下载；这些全是底座运维面的事，业务代码只面向 `FileService`，不感知后端。

## 二、通知：模板 + `MessageService`

### 模板体系：平台默认 + 租户自定义

业务模块在 `BusinessModuleDescriptor.notificationTemplates()` 声明默认模板，启动期落库为平台级（tenant_id=0）；租户主管理员可在后台对模板做租户级定制，**发送时租户定制优先、找不到再回退平台默认**，业务代码无需关心用的是哪份。仓内可运行示例见 `module-crm_demo`：模板 `crm_demo.customer_assigned`（`CrmDemoModule.notificationTemplates()` 声明）+ 客户负责人变更时 `CrmDemoCustomerService` 调 `MessageService.send` 通知新负责人，端到端可跟着调试。

```java
@Override
public List<NotificationTemplateDef> notificationTemplates() {
    return List.of(new NotificationTemplateDef(
            "crm_demo.follow_reminder",                 // code：{module}.{template_name} 全局唯一
            "客户跟进提醒",
            "跟进计划到期前提醒负责人",
            List.of(Channel.STATION, Channel.EMAIL),    // 默认通道
            Map.of(Channel.STATION, TemplateContent.of("跟进提醒", "客户 {customer_name} 计划 {plan_time} 跟进"),
                   Channel.EMAIL,   TemplateContent.of("客户跟进提醒", "您负责的客户 {customer_name} …")),
            List.of(TemplateVariableDef.of("customer_name", "示例客户"),
                    TemplateVariableDef.of("plan_time", "2026-07-01 10:00")),
            Priority.NORMAL));
}
```

约束：`defaultChannels` 里的每个通道都必须在 `contents` 提供文案（启动期校验）；正文用 `{var}` 占位，发送时未传的变量保留占位符不报错。

### 发送 API

业务方同步调 `MessageService.send`，立即返回任务 ID，实际投递经 RocketMQ 异步执行（按 收件人 × 通道 拆分；失败按指数退避延时重投，单条投递最多尝试 3 次——首次 + 重试合计；不可触达标 skipped）：

```java
messageService.send(MessageSendRequest.builder("crm_demo.follow_reminder")
        .variables(Map.of("customer_name", customer.getName(), "plan_time", planTime))
        .recipients(List.of(
                RecipientSpec.member(ownerId),            // 指定成员
                RecipientSpec.role(roleId),               // 某角色全体
                RecipientSpec.dept(deptId, true),         // 部门（true=含子部门）
                RecipientSpec.deptLeader(deptId)))        // 部门负责人
        .channels(List.of(Channel.STATION))               // 不传 = 用模板默认通道
        .category(MessageCategory.BUSINESS)               // 站内信归档分类：SYSTEM / BUSINESS / TODO
        .related("Customer", String.valueOf(customerId))  // 关联业务对象（详情跳转 + 权限探针用）
        .link("/crm-demo/customers/" + customerId)        // 点击跳转的前端路由
        .priority(Priority.IMPORTANT)
        .build());
```

查询聚合状态用 `messageService.status(taskId)`（返回 `Optional`，任务不存在为 empty）。

### 通道与站内信兜底

`Channel` 枚举：`STATION`（站内信）/ `EMAIL` / `SMS` / `WECHAT` / `WECOM` / `DINGTALK`。当前站内信为完整实现，邮件走 Spring Mail（开发环境默认 noop），短信与 IM 通道为占位适配器，接入真实网关时替换对应 `ChannelAdapter` 实现即可，业务代码不变。

- **站内信默认永远兜底**：即使只传 `channels(List.of(Channel.EMAIL))`，也会自动追加站内信，保证用户至少在工作台能看到；确需关闭用 `.noStationFallback(true)`（罕见，需明确理由）。注意兜底通道同样要有文案——只要不关兜底，模板 `contents` 就必须提供 `STATION` 文案（即使 `defaultChannels` 不含它），否则发送时报模板缺通道文案错误。
- **用户通知偏好**：用户可按"通知类别 × 通道"关闭接收，投递前自动跳过（记 skipped 不算失败）；站内信通道强制送达、不受偏好影响。

### 站内信的读取与关联对象降级

站内信读取（列表 / 详情 / 未读数 / 已读）由底座的消息中心统一提供（`MessageInboxService` + 现成端点），业务模块不用自建收件箱。发送时填过 `related(type, id)` 的消息，业务模块可再注册一个 `RelatedObjectAccessChecker`（按 relatedType 路由）：用户后来失去关联对象权限时，消息正文自动替换为"内容已不可见"类占位文案、跳转链接置空，避免调岗后信息泄漏；未注册 checker 默认放行。另外，模板标题里不要拼接高敏感字段（如手机号）——降级只处理正文与跳转，标题始终原样展示。

## 三、接入自查清单

- [ ] 业务附件上传用 `BUSINESS_ONLY` + `ownerModule/ownerRefType/ownerRefId`，业务表只存 `fileId`
- [ ] 有访问控制的业务对象注册了 `FilePermissionChecker`
- [ ] 模板 code 按 `{module}.{name}` 命名；`defaultChannels` 均有对应 `contents` 文案
- [ ] 发送时机在事务成功之后（send 立即入队，事务回滚不会撤回通知）
- [ ] 高敏感字段不进通知标题；带关联对象的消息按需注册 `RelatedObjectAccessChecker`
