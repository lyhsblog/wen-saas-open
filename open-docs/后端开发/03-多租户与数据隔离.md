# 多租户与数据隔离

wen-saas 的多租户隔离方案是**共享库 + tenant_id 自动注入**：所有租户数据在同一个 PostgreSQL schema 里，每张业务表带 `tenant_id` 列，由 MyBatis-Plus 的 `TenantLineInnerInterceptor` 在 SQL 层自动追加 `WHERE tenant_id = ?`（写入同样自动补列）。业务代码**默认零感知**——不查、不传、不校验 tenant_id。本文只讲业务开发必须知道的使用规则。

## 一、tenant_id 列约定

判定原则：这张表的行**有可能属于平台、也有可能属于租户** → 带 tenant_id；行只属于平台 → 不带。

| 表类型 | 例子 | tenant_id 列 |
|---|---|---|
| 纯平台表 | `sys_tenant`、`sys_package`、`sys_business_module` | **不带**（登记进 `platform-only-tables` 白名单，拦截器跳过） |
| 混合表（平台/租户都可能有行） | `sys_user`、`sys_role`、`sys_dict_item` | `BIGINT NOT NULL DEFAULT 0`（0 = 平台行） |
| 纯租户表（**所有业务模块表都是**） | `sys_dept`、`crm_demo_customer` | `BIGINT NOT NULL` |

配套规则：

- **索引前缀必须是 `tenant_id`**：租户内查询全部带 tenant_id，它必须在索引最左侧；
- **业务唯一约束必须含 tenant_id 且是 partial index**（只对活行生效），否则软删一次后编码永远不能复用：

```sql
CREATE UNIQUE INDEX uk_crm_demo_customer_code_alive
    ON crm_demo_customer (tenant_id, code)
    WHERE deleted_at IS NULL;
```

- 平台数据不是特例：平台就是 `tenant_id = 0` 的"特殊租户"（常量 `TenantContext.PLATFORM_TENANT_ID`），`UNIQUE(tenant_id, username)` 之类的约束对平台行同样自然生效。

## 二、自动注入机制（一句话了解即可）

请求进入后，Web 过滤器链解析登录态、把 tenant_id 写进 `TenantContext`（ThreadLocal）；`TenantLineHandlerImpl` 在每条 SQL 执行时从 `TenantContext` 取值：

```
SELECT * FROM crm_demo_customer WHERE name = ?
   →  SELECT * FROM crm_demo_customer WHERE name = ? AND tenant_id = 9001

INSERT INTO crm_demo_customer (name, ...) VALUES (?, ...)
   →  INSERT INTO crm_demo_customer (tenant_id, name, ...) VALUES (9001, ?, ...)
```

`TenantContext` 未设置时直接抛 `IllegalStateException`——宁可报错，也不允许一条不带租户条件的 SQL 溜出去。

因此业务代码的默认写法就是**什么都不做**：Mapper 查询不写 tenant_id 条件，实体的 `tenantId` 字段不手工赋值，Controller / Service 不接收前端传来的任何租户标识（前端也被约定禁止传 `X-Tenant-Id`）。

## 三、TenantContext 用法

`com.wensaas.core.api.tenant.TenantContext`（core-api）：

```java
Long tid = TenantContext.get();       // 可能为 null（未认证链路）
long tid = TenantContext.require();   // 必须存在，否则抛 IllegalStateException

// 在指定租户上下文内执行一段逻辑，结束后自动恢复原上下文（嵌套安全）
TenantContext.runAs(tenantId, () -> { ... });          // 无返回值
Detail d = TenantContext.callAs(tenantId, () -> ...);  // 有返回值

TenantContext.set(tenantId);   // 底层原语：手动 set 的必须自己保证 finally clear
TenantContext.clear();
```

规则：**业务代码优先用 `runAs` / `callAs`**，它们在 finally 中恢复先前上下文，不会泄漏到线程池的下一个任务；裸 `set` 只用于自己完全掌控生命周期的框架级代码。

当前登录用户信息（userId 等）从 `UserContext.require()` 获取，与 TenantContext 同为 ThreadLocal、由过滤器链注入。

## 四、哪些场景必须显式处理

### 1. 异步执行：线程变了，ThreadLocal 就没了

任务中心异步任务、MQ 消费、定时任务、`CompletableFuture` 跨线程——这些场景拦截器照常工作，但 `TenantContext` 是空的，SQL 一执行就抛异常。约定：

- 任务 / 消息投递时**携带 tenant_id 元数据**；
- 消费 / 执行侧用 `TenantContext.runAs(tenantId, ...)` 包住整段业务逻辑。

### 2. 跨租户查询：@CrossTenantQuery，业务模块禁用

平台级聚合（运营看板、健康度统计等）需要绕过 tenant_id 注入时，在方法或类上标注 `com.wensaas.core.api.tenant.CrossTenantQuery`：

```java
@CrossTenantQuery("平台健康度聚合，仅运营链路调用")
List<TenantHealthRow> aggregateAllTenants();
```

硬性规则：

- **仅底座 / 运营级代码可用，业务模块代码禁止引用**该注解——业务模块没有任何合法的跨租户查询场景；
- `@CrossTenantQuery` 只关掉租户过滤这一层；而这类平台聚合通常是 XML / 原生 SQL，`@TableLogic` 的软删自动过滤本就不覆盖手写 SQL，`deleted_at IS NULL` 等条件必须**手写**；
- 面向租户的接口如果按 id 取到了别的租户的数据，对外一律返 404（不暴露存在性），不要返 403。

同理，多表 JOIN 的从表、CTE / 子查询、XML 原生 SQL 中的软删过滤 `AND x.deleted_at IS NULL` 需要人工补齐（`@TableLogic` 自动追加只覆盖简单场景），code review 必查。

### 3. 平台级 / 运营操作：切到目标租户再执行

运营账号登录后 `TenantContext` 是 0；要操作某个租户的数据（目标租户从 URL 路径段取，如 `/api/v1/ops/tenants/{tenantId}/...`），在进业务逻辑前用 `runAs` 切换：

```java
return TenantContext.callAs(targetTenantId, () -> memberService.list(query));
```

业务 service 对此完全无感——它看到的世界永远是"当前租户"。

## 五、新表接入隔离的检查清单

新建一张业务表时逐条过：

1. **DDL**：`tenant_id BIGINT NOT NULL`（业务模块表一律纯租户表）+ `id`（雪花，应用层 `IdType.ASSIGN_ID` 生成）+ `created_at` / `updated_at` / `deleted_at`；
2. **索引**：全部以 `tenant_id` 开头；业务唯一约束用 partial unique index（`WHERE deleted_at IS NULL`）；
3. **实体**：`@TableName` 写全表名（`{module}_` 前缀），字段含 `tenantId`（不手工赋值），软删字段挂 `@TableLogic(value = "null", delval = "now()")`；
4. **不要**把这张表加进 `platform-only-tables` 白名单——那是纯平台表专用的（加了等于关闭该表的租户隔离）；确需新建纯平台表（无 tenant_id 列）时，才在配置 `wen-saas-boot.tenant.platform-only-tables` 中登记；
5. **数据权限（可选）**：表需要按"本人 / 本部门及以下"过滤时，在模块 `BusinessModuleDescriptor.dataPermissionTables()` 声明 `DataPermissionTableDef(resource, resourceName, tableName, creatorColumn, deptColumn)`，并在查询端点挂 `@DataPermission`；没有部门归属列就传 `deptColumn = null`（该表在部门范围下保守不可见）；
6. **验证**：启动应用（表归属、存在性校验在启动期兜底），再用两个不同租户的账号各写一条数据、互查一次，确认互相不可见。

## 六、常见错误速查

| 症状 | 原因 |
|---|---|
| `IllegalStateException: TenantContext 未设置` | 异步 / MQ / 定时任务里没包 `runAs`；或自写线程池丢了上下文 |
| 查询结果混入其他租户数据 | 表被误加进 `platform-only-tables`；或 SQL 走了 `@CrossTenantQuery` 链路 |
| 查询返回已软删的行 | JOIN 从表 / 原生 SQL 少写 `deleted_at IS NULL` |
| 同编码软删后无法重建 | 唯一索引没写成 partial（缺 `WHERE deleted_at IS NULL`） |
| 启动报表归属校验失败 | 表名没用 `{module}_` 前缀，或迁移脚本没建表 |
