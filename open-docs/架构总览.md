# 架构总览

wen-saas 是一个多租户 SaaS 管理后台底座：后端是一个可插装业务模块的 Spring Boot 单体，前端是覆盖运营端 / 租户端 / 移动端三种形态的 pnpm monorepo。底座把多租户隔离、权限、自定义字段、异步任务、通知、文件、审计这些"每个 toB 系统都要重做一遍"的能力做成基础设施；你作为业务开发者，交付的是一个"后端 SPI 模块 + 前端模块"组成的业务包，插进底座即可运行。本篇只讲整体形状，各机制的细节见文末的专篇地图。

## 一、系统形态

```
        ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
        │   ops-web   │  │ tenant-web  │  │     h5      │
        │ 平台运营端  │  │ 租户管理后台│  │ 租户移动端  │
        │  React+antd │  │  React+antd │  │ antd-mobile │
        └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
               │                │                │
               └────────── REST /api ────────────┘
                                │
        ┌───────────────────────▼───────────────────────┐
        │          后端单体（单一 Spring Boot jar）      │
        │                                               │
        │   ┌───────────────────────────────────────┐   │
        │   │ core 底座：多租户 / 权限 / 自定义字段 │   │
        │   │ 任务中心 / 通知 / 文件 / 审计 / SPI   │   │
        │   └───────▲───────────▲───────────▲───────┘   │
        │           │ core-api  │           │           │
        │      业务模块 A   业务模块 B   业务模块 N     │
        └───────┬───────────┬───────────┬───────────────┘
                │           │           │
        ┌───────▼──┐  ┌─────▼────┐  ┌───▼────────┐
        │PostgreSQL│  │  Redis   │  │ RocketMQ 5 │
        │ 主数据库 │  │缓存/会话 │  │ 事件/异步  │
        └──────────┘  └──────────┘  └────────────┘
          外围：对象存储（本地 / OSS 可切换）；定时调度内嵌于应用（Quartz）
```

部署形态刻意保持简单：一个 jar、一套 PG + Redis + RocketMQ。多租户不拆库不拆实例，靠共享库 + `tenant_id` 隔离；水平扩展靠多实例跑同一个 jar（会话在 Redis、定时任务靠 Redis 锁单跑，天然无状态）。整个应用够轻——单 jar 冷启动本地实测约 **5 秒** 即对外就绪，滚动/蓝绿发布时新实例上线快、切流量等待短。

## 二、后端工程分层（wen-saas-boot）

```
wen-saas-boot/
├── core/
│   ├── core-api/    扩展点接口与模型：BusinessModuleDescriptor、各注册表 API、领域模型
│   ├── core-impl/   底座实现：SPI 注册、多租户、权限、缓存、消息、文件、操作日志，以及认证 / 租户上下文 / 审计 / Request ID 等全局过滤器
│   └── core-web/    Web 层：底座 REST 控制器、统一异常处理、JSON / 分页公共件、API 文档配置
├── modules/         业务模块聚合，每个业务模块一个 maven 子模块
│   └── module-crm_demo/   示例模块：覆盖 SPI 全部扩展点的端到端活样例（自定义字段 / 数据权限 / 导入导出 / 审计 / 事件 / 定时任务…）
└── app/             启动器：app 的 pom 决定本次部署装配哪些业务模块，打出单一可执行 jar
```

依赖方向自上而下单向：`app → core-web + 各业务模块`，`core-web → core-impl → core-api`。

业务模块的规则是：

- **maven 上依赖 `core/core-web`**（一站拉齐 core-impl / core-api、MyBatis-Plus、spring-web）；
- **代码上只面向 `core/core-api` 编程**——调用底座的方式只有两种：core-api 暴露的接口 / 扩展点，以及事件总线。不 import core-impl 的内部实现，也不直接调用其他业务模块的 API；
- 模块内部自成一体：自己的 `controller / service / repository / entity`、自己的 Flyway 脚本目录（`src/main/resources/db/migration/{module_code}/`）、一个实现 `BusinessModuleDescriptor` 的入口 Bean。

`BusinessModuleDescriptor`（见 `wen-saas-boot/core/core-api/src/main/java/com/wensaas/core/api/spi/`）是模块与底座的全部契约：一处声明模块元数据、API 路径前缀、权限点、数据权限表、自定义字段对象、字典分组、通知模板、导入实体、任务处理器、合规导出对象、事件订阅、工作台卡片、H5 页面、定时任务等全部贡献点。API 路径前缀按用途分两类——业务端点（登录态）走 `/api/v1/biz/{code}/`、开放 API（AppKey 鉴权）走 `/api/v1/openapi/{code}/`，二者均由 `apiPathPrefixes()` 声明、`PackageStatusWebFilter` 按租户套餐拦截。底座启动时通过 Spring 容器收集所有该接口的 Bean，逐一校验注册——冲突（如 API 前缀撞车、命名空间越界）会直接阻断启动。部署组合由 `app/pom.xml` 决定：加一个 `<dependency>` 就装上一个模块。

## 三、前端 monorepo 结构（wen-saas-frontend）

```
wen-saas-frontend/          pnpm workspace（apps/* + packages/* + modules/*）
├── apps/
│   ├── ops-web/            平台运营端（管租户、套餐、运营人员）
│   ├── tenant-web/         租户管理后台（租户日常使用的 PC 端）
│   └── h5/                 租户移动端（antd-mobile）
├── packages/               共享基座包（@wen-saas/*）
│   ├── api-client/         REST 客户端封装（按领域拆分）+ 表单错误映射
│   ├── auth/               登录态与会话监听
│   ├── domain/             领域类型，含由后端 OpenAPI 文档生成的契约类型（从运行实例导出后生成）
│   ├── design-system/      设计令牌 tokens.css + antd 主题
│   ├── shared-ui/          通用业务组件（AppShell、DataTable、DangerConfirm…）
│   ├── permissions/        权限/套餐门控组件（PermissionGate、PackageGate、水印…）
│   ├── module-runtime/     前端业务模块 SPI：manifest 类型 + 模块 registry
│   ├── config/             环境配置
│   └── utils/              工具函数
└── modules/                前端业务模块（与后端业务模块一一对应）
    └── base/               底座模块（工作台、字典等通用页面的模块身份）
```

前端模块机制与后端对齐：每个前端模块提供一份 `manifest.ts`（实现 `module-runtime` 的 `BusinessModuleManifest`，code / name / version 与后端模块一致），声明自己贡献的路由（懒加载组件，入口 app 按需 code-split）。入口 app 在构建期用 `registerModules([...])` 注册模块，不做远程动态加载。导航菜单不由前端 manifest 声明，而是吃后端下发的能力集（菜单树以数据库为权威），权限点判定走 `permissions` 包的门控组件。

后端 Long 型主键（雪花 id）在 JSON 中序列化为字符串，前端类型一律用 `string` 承接，不要转 number。

## 四、技术栈一览

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 / 运行时 | Java 25 (LTS) | 启用虚拟线程处理 IO 密集型请求；底座开发环境:temurin-25.0.3 |
| 应用框架 | Spring Boot 4.0.x | 单体，单 jar 部署，冷启动约 5 秒就绪 |
| ORM | MyBatis-Plus 3.5.x | 保留 SQL 可见性，便于复杂查询 |
| 数据库 | PostgreSQL 18.4 | jsonb + 表达式索引是自定义字段的基石 |

| 缓存 / 会话 | Redis 8.0.6 | Redis 为权威缓存与会话层；热点读走 `CacheRegion`（`core-api` 的 `cache` 包；Redisson RLocalCachedMap：进程内 L1 + Redis L2，写后 evict 经 pub/sub 广播失效） |

| 路由 | react-router 7 | |
| UI 组件 | antd 6（PC 双端）/ antd-mobile 5（h5） | 共享 design-system 令牌 |
| 测试 | Vitest + Testing Library + Playwright + MSW | 单测 / E2E / mock |

## 六、业务模块扩展模型总述

在这套底座上做一个业务模块，交付物是对称的两半：

1. **后端 SPI 模块**：`wen-saas-boot/modules/` 下新建 maven 子模块，写业务表的 Flyway 脚本、实体 / 服务 / Controller，提供一个 `BusinessModuleDescriptor` 实现声明模块的全部贡献（API 路径前缀、权限点、数据权限表、自定义字段对象、字典分组、通知模板、导入实体、任务处理器、合规导出对象、事件订阅、工作台卡片、H5 页面、定时任务），最后在 `app/pom.xml` 里装配。用不到的贡献点返回空列表即可，不必全部实现。
2. **前端模块**：`wen-saas-frontend/modules/` 下新建 workspace 包，写页面组件与 `manifest.ts`（贡献懒加载路由），在目标 app 入口 `registerModules` 注册；API 调用与类型走 `api-client` / `domain`，UI 与权限门控复用 `shared-ui` / `permissions`。

多租户过滤、认证、权限拦截、审计落库全部由底座在框架层完成，模块代码里不出现 `tenant_id`。`wen-saas-boot/modules/module-crm_demo/`（客户管理 Demo）把上表每一项底座能力都用真实业务串了一遍——自定义字段、数据权限、导入导出、审计、领域事件与订阅、定时任务、文件附件、工作台卡片、开放 API、H5 页面……每篇接入指南都能在它里面找到对应的可运行示例，建议对照它起步。

分步骤的上手教程见[后端业务模块开发系列](README.md#后端业务模块开发)与[前端开发系列](README.md#前端开发)。
