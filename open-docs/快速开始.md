# 快速开始

本指南面向第一次接触 wen-saas 的开发者，目标是在约 30 分钟内于本机跑起完整系统：后端服务 + 前端三端（运营后台 / 租户后台 / 移动端 H5）。

## 1. 环境要求

| 组件 | 版本 | 说明 |
|---|---|---|
| Docker Desktop | 较新版本（Compose v2） | 承载 PostgreSQL / Redis / RocketMQ 中间件 |
| JDK | 25 | 后端为 Java 25 + Spring Boot 4 |
| Maven | 3.9+ | 构建后端多模块工程 |
| Node.js | 24.x（`>=24 <25`） | 前端 monorepo |
| pnpm | 11.2.2（经 Corepack 启用） | 前端包管理器 |

仓库目录结构（后端与前端在同一个 git 仓库中）：

```
wen-saas/
├── wen-saas-boot/       后端
├── wen-saas-frontend/   前端（ops-web / tenant-web / h5）
└── open-docs/           使用与扩展文档（即本文档）
```

## 2. 启动中间件（Docker Compose）

中间件编排在 `wen-saas-boot/local_environment/docker-compose.yml`，包含：PostgreSQL 18、Redis 8、RocketMQ 5.3.2（NameServer + Broker + 独立 Proxy + 一次性 topic 初始化容器 + Dashboard）。

### 2.1 准备 `.env`

compose 文件里的密码走环境变量，**必须先在 `local_environment/` 下创建 `.env`**（仓库提供了 `.env.example`，`.env` 本身不入 git）：

```bash
cd wen-saas-boot/local_environment

cp .env.example .env    # 默认 POSTGRES_PWD=root / REDIS_PWD=root，可按需修改
```

> 数据目录无需预建：compose 里各服务直接 bind 挂载 `./data/` 下各自子目录，目录缺失时 Docker 会自动创建。首次启动请确保 `./data` 不存在或为空；以后要彻底重置数据，`docker compose down` 后删除 `./data` 目录即可。

> 密码建议就用 `root`：后端 dev 配置（`app/src/main/resources/application-dev.yml`）默认按 `postgres/root`、Redis 密码 `root` 连接。如果你改了 `.env`，记得同步改 dev 配置或用环境变量覆盖。

### 2.2 宿主机 hosts（必须）

RocketMQ Broker 对外通告的地址是 `host.docker.internal`，宿主机上的后端进程需要能解析它。在 `/etc/hosts` 加一行：

```
127.0.0.1 host.docker.internal
```

> 若你在用 Clash / Surge 等代理且开启 fake-ip 模式，这一行是**必须**的，不是可选项——否则 DNS 会被劫持成假 IP，MQ 发送静默失败（异步任务永久 pending）。

### 2.3 启动

```bash
docker compose up -d
```

验证：

```bash
docker compose ps                        # postgreSQL-18 / redis / rocketmq-* 应为 Up
docker logs rocketmq-topic-init          # 末行应为 "all topics ready"
```

`rocketmq-topic-init` 是一次性容器：等 Broker 注册后自动预建后端消费者订阅的 10 个 topic 然后退出（`ps` 里看不到它属正常）。RocketMQ 5.x gRPC 消费者要求 topic 预先存在，这一步没做后端会起不来。

### 2.4 创建数据库

PostgreSQL 容器只自带默认的 `postgres` 库，后端使用的 `wen_saas` 库需要手动建一次：

```bash
docker exec postgreSQL-18 psql -U postgres -c 'CREATE DATABASE wen_saas'
```

表结构与初始数据无需手动导入——后端启动时由 Flyway 自动迁移（见第 4 节）。

## 3. 构建并启动后端

```bash
cd wen-saas-boot
mvn clean package -DskipTests
java -jar app/target/wen-saas-boot-app.jar --spring.profiles.active=dev
```

说明：

- 建议加 `-DskipTests`：部分集成测试会连本机真实数据库，首次空库构建时直接跳过最省事。
- 后端监听 **8080** 端口（`server.port`，可用环境变量 `SERVER_PORT` 覆盖）。
- dev profile 的连接约定：PostgreSQL `127.0.0.1:5432`（库 `wen_saas`，用户 `postgres/root`）、Redis `127.0.0.1:6379`（密码 `root`）、RocketMQ Proxy gRPC `127.0.0.1:8081`。
- 启动快：单 jar 冷启动本地实测约 **5 秒** 即完成初始化——控制台会打印一行启动横幅 `Wen SaaS Boot v… 已就绪 · profile=dev · 端口 8080 · 启动耗时 5.x 秒`，看到它就表示已就绪，比 curl 更直观。
- 健康检查：`curl http://localhost:8080/actuator/health` 返回 `UP` 即成功。

## 4. 数据库初始化与初始账号

后端首次启动时 Flyway 会在 `wen_saas` 空库上自动执行全部迁移（建表 + 种子数据），无需任何手工 SQL。

种子数据中预置了**运营端超管**：

| 项 | 值 |
|---|---|
| 账号 | `admin@ops` |
| 初始密码 | `admin123` |

> 首次登录后请立即修改密码。dev 环境运营端登录不强制 MFA。
> 该账号邮箱不在种子 SQL 里（邮箱列是密文），由应用首次启动按
> `wen-saas-boot.ops.initial-admin-email`（环境变量 `WEN_SAAS_BOOT_OPS_INITIAL_ADMIN_EMAIL`）加密回填，建议部署时改成自己的运维邮箱。

如果本地库曾经跑坏想彻底重来，可执行 `local_environment/reset.sql`（`DROP SCHEMA public CASCADE` 后重建），再重启后端让 Flyway 从头迁移：

```bash
docker exec -i postgreSQL-18 psql -U postgres -d wen_saas < local_environment/reset.sql
```

## 5. 启动前端三端

```bash
cd wen-saas-frontend
corepack enable
corepack prepare pnpm@11.2.2 --activate
pnpm install
```

三端各自独立启动（可只起需要的端）：

```bash
pnpm dev:ops       # 运营后台   http://ops.localhost:5173
pnpm dev:tenant    # 租户后台   http://{租户编码}.localhost:5174
pnpm dev:h5        # 移动端 H5  http://{租户编码}.m.localhost:5175
```

租户与 H5 端**由子域名区分租户**（`{租户编码}.localhost`），运营端固定 `ops.localhost`。现代浏览器（Chrome/Edge/Firefox）会把任意 `*.localhost` 自动解析到 `127.0.0.1`，本地**无需改 hosts**——直接在地址栏用上面带子域名的 URL 访问即可。

三端的 Vite dev server 均已配置代理，把 API 请求转发到 `http://127.0.0.1:8080`，前端无需任何额外配置即可对接本地后端（后端 CORS 也已放行这三个端口）。

## 6. 登录验证

### 6.1 运营后台

1. 打开 `http://ops.localhost:5173/login`；
2. 用 `admin@ops` / `admin123` 登录，进入运营工作台。

### 6.2 租户后台（需先在运营端开通租户）

系统没有预置租户，需在运营后台创建：

1. 运营后台 → 租户管理 → 开通租户，按向导填写租户编码、名称、套餐，以及主管理员的账号 / 手机 / 邮箱；
2. 开通完成页会生成一条 **48 小时有效的密码设置链接**（形如 `http://<租户编码>.localhost:5174/reset-password/<token>`），复制并在浏览器打开，为主管理员设置初始密码；
3. 打开 `http://<租户编码>.localhost:5174/login`，用主管理员账号 + 刚设置的密码登录。

> 租户端由**子域名**区分租户（`<租户编码>.localhost:5174`），URL 不再带租户编码路径前缀；用 curl 直调 `/api/auth/login` 时租户账号要额外传 `tenantCode` 字段（运营账号不传）。

### 6.3 移动端 H5

打开 `http://<租户编码>.m.localhost:5175/login`，用租户账号登录（建议浏览器开移动端仿真视口）。

## 7. 常见问题

**后端启动报 `Failed to start RocketMQ push consumer` / `Stream is already completed`**
- Proxy 的 gRPC 端口映射必须保持 `8081:8081`（宿主 = 容器一致），**不能重映射**。RocketMQ 5.x 客户端会按 Proxy 自报的端口回连建 telemetry 流，重映射后连不上。
- 自建 Proxy 是明文 gRPC，客户端必须关 TLS：dev 配置里 `rocketmq.producer.ssl-enabled: false`，消费者注解侧也已写死 `sslEnabled=false`——自行扩展消费者时别漏这个。
- 确认 topic 已预建：`docker logs rocketmq-topic-init` 末行是 `all topics ready`。若删除过 `./data` 数据目录，重跑 `docker compose up -d` 会再次触发 init 容器。

**MQ 消息发送静默失败（异步任务一直 pending）**
- 多半是 `host.docker.internal` 解析被代理软件 fake-ip 劫持，按 2.2 节在 `/etc/hosts` 加 `127.0.0.1 host.docker.internal`，然后重启后端。

**Flyway 报 `relation "sys_tenant" does not exist` 或迁移被跳过**
- 库不是"真正的空库"（残留了序列 / 历史表）导致 baseline 误判。用第 4 节的 `reset.sql` 彻底清空 schema 后重启后端。

**端口冲突**
- 本方案占用：5432（PG）、6379（Redis）、9876 / 10909 / 10911 / 10912（RocketMQ）、8081（Proxy gRPC，不可改映射）、18080（Proxy HTTP）、18082（RocketMQ Dashboard）、8080（后端）、5173 / 5174 / 5175（前端三端）。
- 后端端口可用 `SERVER_PORT` 环境变量改；但改了要同步改前端各 `apps/*/vite.config.ts` 的 proxy target。

**改了 `local_environment/conf/broker.conf` 后不生效**
- 需 `docker restart rocketmq-broker` 并**重启后端**（运行中的 producer 缓存了旧路由）。

**RocketMQ Dashboard**
- `http://localhost:18082` 可查看 Broker / Topic / 消费进度，排查 MQ 问题时很有用。
