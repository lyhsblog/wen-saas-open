# 部署指南

面向将 wen-saas 部署到自有环境的采用方，描述系统的部署形态、后端 / 前端部署步骤与中间件要求。

## 一、部署形态总览

```
                    ┌──────────────────────────────┐
  ops.example.com   │  Nginx（静态托管 + API 反代） │
  *.example.com   ──►  ops-web / tenant-web / h5   │
  *.m.example.com   │  /api → 后端 8080            │
                    └────────────┬─────────────────┘
                                 │
                    ┌────────────▼─────────────────┐
                    │  wen-saas-boot-app.jar（单进程）│
                    └──┬──────────┬──────────┬─────┘
                       │          │          │
                  PostgreSQL    Redis    RocketMQ 5（Proxy gRPC）
```

- **后端**：单个 Spring Boot fat jar（`wen-saas-boot-app.jar`），一个进程承载全部能力，可按需水平扩展多实例。
- **前端**：三份纯静态站点（运营端 `ops-web`、租户端 `tenant-web`、移动端 `h5`），任意静态服务器可托管，推荐 Nginx。租户由**子域名**区分（每租户一个专属子域），详见 3.2 / 3.3。
- **中间件**：PostgreSQL + Redis + RocketMQ 5，三者为硬依赖；定时任务由应用内嵌 Quartz 调度，不需要独立调度中心。

## 二、后端部署

### 2.1 打包

环境要求：JDK 25、Maven 3.9+。

```bash
cd wen-saas-boot
mvn clean package -pl app -am -DskipTests
# 产物：app/target/wen-saas-boot-app.jar
```

### 2.2 运行与 profile

配置文件按 profile 分层：`application.yml`（公共）+ `application-{dev,test,prod}.yml`。生产环境激活 `prod`，所有敏感配置不入 git，全部由环境变量注入（缺失即启动失败，属有意设计）：

```bash
SPRING_PROFILES_ACTIVE=prod java -jar wen-saas-boot-app.jar
```

### 2.3 关键环境变量（prod）

| 环境变量 | 说明 | 必填 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | 固定 `prod` | 是 |
| `SPRING_DATASOURCE_URL` | 如 `jdbc:postgresql://db-host:5432/wen_saas` | 是 |
| `SPRING_DATASOURCE_USERNAME` / `SPRING_DATASOURCE_PASSWORD` | 数据库账号 | 是 |
| `WEN_SAAS_BOOT_REDIS_HOST` / `WEN_SAAS_BOOT_REDIS_PASSWORD` | Redis 地址与密码 | 是 |
| `WEN_SAAS_BOOT_REDIS_PORT` / `WEN_SAAS_BOOT_REDIS_DATABASE` | 默认 `6379` / `0` | 否 |
| `WEN_SAAS_BOOT_ROCKETMQ_ENDPOINTS` | RocketMQ **Proxy 的 gRPC 端点**（如 `mq-host:8081`），不是 NameServer 地址 | 是 |
| `WEN_SAAS_BOOT_ROCKETMQ_SSL` | 自建明文 Proxy 保持默认 `false` | 否 |
| `WEN_SAAS_BOOT_JWT_SECRET` | JWT HS256 秘钥，**至少 32 字节**，务必替换 | 是 |
| `WEN_SAAS_BOOT_FILE_AES_KEY` | 文件凭证加密密钥（Base64 编码的 32 字节），务必替换 | 是 |
| `WEN_SAAS_BOOT_PLATFORM_OSS_ENDPOINT` / `_BUCKET` / `_AK` / `_SK` | 平台默认对象存储（prod 默认阿里云 OSS） | 见下 |
| `SPRING_MAIL_HOST` / `_USERNAME` / `_PASSWORD`（`_PORT` 默认 465） | SMTP，配齐后另将 `wen-saas-boot.notification.email-noop` 改为 `false` 才真发邮件 | 否 |
| `WEN_SAAS_BOOT_OPS_INITIAL_ADMIN_EMAIL` | 初始运营超管邮箱：邮箱列是密文、迁移 SQL 不写，首次启动该账号邮箱为空时加密回填 | 否 |
| `SERVER_PORT` | 默认 `8080` | 否 |

说明：

- **对象存储**：prod 默认后端为 `aliyun_oss`，四个 OSS 变量必须提供。不使用阿里云 OSS 时用启动参数覆盖后端，例如本地磁盘 `--wen-saas-boot.file.platform-default-backend=local`（多实例需共享挂载），腾讯云 COS 为 `tencent_cos`（凭证走 `WEN_SAAS_BOOT_PLATFORM_COS_*` 系列变量）。
- **定时任务**：内嵌 Quartz JDBC 集群模式，无外部调度中心；调度表（11 张 `qrtz_` 表）由 Flyway 建在 PG 独立 `quartz` schema，与业务表隔离。默认 `wen-saas-boot.jobs.enabled=true` 开箱即跑。各任务 cron 默认值在代码内，可按任务覆盖（如 `--wen-saas-boot.jobs.cron.tenant-expire="0 5 0 * * ?"`），改动在下次启动时以代码/配置为准同步进库。多实例部署时集群保证一次触发只有一个节点执行，停机漏跑的任务恢复后补跑一次；执行体外还有一道 Redis 分布式锁兜底。设 `--wen-saas-boot.jobs.enabled=false` 的节点不装配任务、也不参与调度集群（可用于「Web 节点不跑任务」的分工部署，但至少要有一个开着的节点）；全部节点都关闭则所有定时能力停摆——包括日志分区表的月度分区预建、租户到期处理、工单 SLA 扫描与自动关闭、软删文件/自定义字段等各类过期数据清理，需自行安排等价的运维手段。
- 短信通道默认 noop（仅打日志），接入阿里云短信时配置 `ALIYUN_SMS_AK` / `ALIYUN_SMS_SK` / `ALIYUN_SMS_SIGN` 并设 `WEN_SAAS_BOOT_SMS_NOOP=false`。
- **登录二步验证**：所有账号默认可选（个人中心自助开关，通道自动推导——已绑身份验证器用 TOTP，否则邮箱验证码）。对运营侧有强合规要求时设 `wen-saas-boot.auth.ops-mfa-enforced=true`：未开启的运营账号登录时将被强制完成二步验证配置。
- **邮件防护**：全局当日发送量硬上限 `wen-saas-boot.notification.email-daily-limit`（≤0 不限）；收件人黑名单 `wen-saas-boot.notification.email-blacklist`（列表，大小写不敏感精确匹配，命中不真发、按成功处理且不占配额，适合测试环境屏蔽真人邮箱）。
- **收发分离（可选）**：`wen-saas-boot.mq.consumers-enabled`（默认 `true`）控制本进程是否装配 MQ 消费者。多实例部署想把 Web 请求节点与异步消费节点分开时，Web 节点以 `--wen-saas-boot.mq.consumers-enabled=false` 启动即只发不收，全部消费（审计、通知、任务、webhook 等）由保持默认值的 worker 节点承担；至少要有一个开着消费者的实例，否则异步链路只堆积不处理。

### 2.4 数据库迁移

应用启动时 Flyway 自动执行迁移，无需手工建表：底座迁移与各业务模块迁移分目录、各用独立 history 表，按版本顺序补齐未应用的脚本。首次启动前只需创建空库（如 `wen_saas`）并授权。

### 2.5 健康检查

| 端点 | 用途 |
|---|---|
| `GET /actuator/health` | 总体健康（prod 不含细节） |
| `GET /actuator/health/liveness` | 存活探针 |
| `GET /actuator/health/readiness` | 就绪探针（滚动 / 蓝绿切流依据） |
| `GET /actuator/info` | 版本信息 |
| `GET /actuator/prometheus` | Prometheus 指标抓取 |

Actuator 端点仅供内网监控使用，**不要经网关暴露到公网**（网关只放行 `/api`）。

## 三、前端部署

### 3.1 构建

环境要求：Node.js 24（`>=24 <25`）、pnpm。

```bash
cd wen-saas-frontend
corepack pnpm install
corepack pnpm build
# 产物：dist/ops-web、dist/tenant-web、dist/h5 三份独立静态站
```

也可用 `pnpm build:ops` / `build:tenant` / `build:h5` 单独构建某一端。

**基础域注入**：租户端 / H5 端从子域名解析当前租户，构建时须提供各端「基础域」环境变量 `VITE_TENANT_BASE_DOMAIN`（Vite 构建期注入）：租户端 = 面向租户的顶级域（如 `example.com`）、H5 端 = H5 顶级域（如 `m.example.com`）。前端将 hostname 去掉基础域后的首段作为租户标识（tenantCode）、裸域视为无租户。仓库内 `apps/tenant-web/.env.production`、`apps/h5/.env.production` 给了示例值，按自有域名替换后再 `build`。运营端自身无租户位、不需要 `VITE_TENANT_BASE_DOMAIN`，但需要 `VITE_TENANT_WEB_ORIGIN`（租户端**裸域 origin**，如 `https://example.com`）：运营端生成指向租户端的链接（代登录兑换、密码重置链接、租户登录页）时，会把租户 code 作为子域前缀拼到该 origin 上（如 `https://acme.example.com/impersonate-redeem`），示例值见 `apps/ops-web/.env.production`。

### 3.2 域名规划

租户由**子域名**区分（每个租户一个专属子域，租户标识不放在 URL 路径里），三端域名规划：

| 端 | 示例域名 | 说明 |
|---|---|---|
| 运营端 ops-web | `ops.example.com` | 平台运营人员使用，建议加内网 / IP 白名单；无租户位、固定单域名 |
| 租户端 tenant-web | `{租户code}.example.com`（通配 `*.example.com`） | 每租户一个子域，如 `acme.example.com`；裸域 `example.com` 作无租户落地 / 选择页 |
| 移动端 h5 | `{租户code}.m.example.com`（通配 `*.m.example.com`） | 每租户一个 H5 子域，如 `acme.m.example.com` |

前端从子域名解析当前租户，因此：

- 构建时须用 `VITE_TENANT_BASE_DOMAIN` 注入各端「基础域」（租户端 `example.com` / H5 端 `m.example.com`，见 3.1）。
- **租户 code 即子域名 label**：后端已强制其符合 DNS 主机名规范（小写字母 / 数字 / 连字符、不以连字符起止、2–32 位），并把平台端 / 基础设施子域名前缀（`ops`、`m`、`www`、`api`、`mail`、`admin`、`app`、`cdn`、`static`、`mobile`、`actuator`）列为保留字拒绝注册，避免与端域名 / 静态资源冲突。

**运营端与租户端必须分开顶级子域**：两端登录会话按浏览器源（origin）隔离——refresh token 走 host-only cookie、access token 存各端 `localStorage`；运营端固定 `ops.example.com`，与各租户子域天然不同源，不会相互覆盖。

> **会话 token 存储方式**
>
> refresh token 由后端以 **httpOnly + Secure + SameSite=Strict cookie**（名 `wen_rt`、`Path=/api/auth`、**host-only 不设 `Domain`**）下发，浏览器随刷新请求自动携带，JS 不可读——XSS 无法窃取 refresh。access token（短时效，默认 15min）存 `localStorage` 经 `Authorization` header 带出。
>
> 部署要点：
> - **务必保持 refresh cookie 为 host-only**（后端默认如此，不要人为加 `Domain=.example.com`），否则运营端与各租户子域会共享 refresh、相互覆盖登录态。
> - **prod 必须 HTTPS**：cookie 带 `Secure`（`wen-saas-boot.auth.refresh-cookie-secure` 默认 `true`），http 环境浏览器不会存该 cookie。
> - 前端与 API **同源反代**（每子域 `/api` 反代到后端，见 3.3），refresh cookie 才能随同源 XHR 正确携带；若前后端分域需自行处理 CORS 凭证与 cookie 属性。
> - 建议在网关统一下发严格 CSP（脚本白名单 + 禁内联）进一步收敛 XSS 面；refresh token 轮换 + 重用检测即时吊销是被盗后的第二道闸。

### 3.3 Nginx 托管与 API 反代

推荐前端与 API 同源：每个站点将 `/api` 反代到后端，前端零跨域。租户端 / H5 端各用**一套通配子域 server** 承载全部租户，运营端独立 server。示例（替换域名与 root；三个 server 的 `/api` 反代同构，抽到 `proxy_headers.conf`）：

```nginx
# 运营端（精确子域，优先匹配）
server {
    listen 443 ssl;
    server_name ops.example.com;
    root /var/www/wen-saas/ops-web;          # 对应 dist/ops-web
    location /     { try_files $uri $uri/ /index.html; }
    location /api/ { proxy_pass http://127.0.0.1:8080; include proxy_headers.conf; }
    # 登录页服务状态探测用；只放行 health，其余 actuator 端点不对外
    location = /actuator/health { proxy_pass http://127.0.0.1:8080; include proxy_headers.conf; }
}

# H5 端（m 入口 + 每租户 *.m 子域，两层需单列）
server {
    listen 443 ssl;
    server_name m.example.com *.m.example.com;
    root /var/www/wen-saas/h5;               # 对应 dist/h5
    location /     { try_files $uri $uri/ /index.html; }
    location /api/ { proxy_pass http://127.0.0.1:8080; include proxy_headers.conf; }
}

# 租户端（通配子域，每租户一个子域；ops. 与 m. 已被上面精确 server 抢占）
server {
    listen 443 ssl;
    server_name *.example.com;
    root /var/www/wen-saas/tenant-web;       # 对应 dist/tenant-web
    location /     { try_files $uri $uri/ /index.html; }
    location /api/ { proxy_pass http://127.0.0.1:8080; include proxy_headers.conf; }
}
```

`proxy_headers.conf`（认证走 Authorization 头与请求体，反代原样透传即可）：

```nginx
proxy_set_header Host $host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
client_max_body_size 120m;                   # 与后端上传上限对齐
```

要点：

- **子域名分流靠 nginx 精确 `server_name` 优先于通配**：`ops.example.com` / `m.example.com` 精确命中各自 server，其余 `*.example.com` 落到租户端。故租户 code 不能取 `ops` / `m` / `www` 等端前缀（后端已按保留字拒绝，见 3.2）。
- **DNS**：为 `*.example.com`、`m.example.com`、`*.m.example.com` 配通配 / 精确解析到服务器。
- **TLS 通配证书**：一张证书覆盖全部租户 —— SAN 含 `example.com`、`*.example.com`、`*.m.example.com`（`*.` 只覆盖一层子域，故 H5 的两层 `*.m.` 需单列）；通配证书按 DNS 验证方式签发。
- SPA 前端路由回退由 `try_files ... /index.html` 承担；nginx 只把 `/api/` 反代到后端 8080，不感知租户（租户身份由登录态 JWT 承载）。
- 后端已配置 `server.forward-headers-strategy: framework`，反代必须带 `X-Forwarded-Proto` / `X-Forwarded-For`，否则后端生成的绝对链接协议会出错。
- 同源反代下无需 CORS；若坚持前后端分域，需修改后端 `wen-saas-boot.web.cors.allowed-origins` 为前端域名（默认值是本地开发端口，生产同源部署可清空）。生产 CSP 等安全响应头由网关统一下发，构建产物本身不内置。

## 四、中间件要求

| 中间件 | 版本基线 | 说明 |
|---|---|---|
| PostgreSQL | 18 | 唯一数据库；建库后交给 Flyway 自动建表 |
| Redis | 8.0 | 会话 / 缓存 / 限流，客户端为 Redisson |
| RocketMQ | 5.3.2 | 审计、通知、任务、事件等异步链路 |

RocketMQ 5 注意点（踩坑高发区）：

1. **客户端走 Proxy 的 gRPC 端口**（默认 8081），`WEN_SAAS_BOOT_ROCKETMQ_ENDPOINTS` 填 Proxy 地址而非 NameServer 的 9876。
2. 推荐 **NameServer + Broker + 独立 Proxy（CLUSTER 模式）** 的拓扑；容器化部署时 Proxy 的 gRPC 端口宿主机与容器必须一致（Proxy 会向客户端自报该端口，重映射会导致消费者启动失败）。
3. **启动前预建 topic**：v5 消费者启动期严格校验路由，topic 不存在即启动失败，不能依赖自动建 topic。需预建以下 10 个：`wen_audit_operation`、`wen_audit_login`、`wen_notify_station`、`wen_notify_email`、`wen_notify_sms`、`wen_notify_im`、`wen_task_execute`、`wen_api_call_log`、`wen_event`、`wen_webhook_send`（后两个是事件与 webhook 推送链路，见 [Webhook 事件推送](后端开发/11-Webhook事件推送.md)）。**其中 `wen_webhook_send` 必须建成 DELAY 类型**（建 topic 时带属性 `-a +message.type=DELAY`）——webhook 的失败重试靠延时消息实现，v5 同一 topic 只接受声明的消息类型，建成默认 NORMAL 会导致重试消息被 broker 拒收（首发不受影响，问题只在失败重试时暴露）。其余 9 个 NORMAL 即可。
4. 自建明文 Proxy 保持 `ssl-enabled=false`；接入 TLS 托管服务（如云厂商 ONS）需要额外的代码级适配，不是改一个开关就能切换。

## 五、CI/CD 边界

底座**不内置任何 CI/CD 流水线**（无 GitHub Actions / GitLab CI 配置），因为各采用方的发布流程、制品库与审批规范差异太大。请按自己的流程搭建，典型骨架：编译打包 → 制品归档（jar / 镜像）→ 部署 → `/actuator/health/readiness` 通过后切流量。数据库 schema 遵循前向兼容原则演进，回滚应用版本时无需回滚 schema。

## 六、演示环境守卫（可选）

对外演示站通常会把管理员账号开放给访客。RBAC 挡不住"持有角色管理权限的账号自提权"（把任意权限点加回自己可及的角色），所以底座提供一层独立于权限模型的**接口黑名单守卫**：按「HTTP 方法 + Ant 路径」拦截写操作，命中直接返回 403（`DEMO_GUARD_FORBIDDEN`，提示"演示环境已禁用该操作"），对所有请求方生效——访客即便自建账号、改角色也绕不过。

默认关闭，零开销；开启只需部署配置：

```yaml
wen-saas-boot:
  demo-guard:
    enabled: true
    rules:
      # 格式："方法[,方法] Ant路径"，启动时校验，格式非法直接启动失败
      - "POST,PUT,DELETE /api/v1/ops/menus/**"          # 菜单管理禁写（删除不可恢复）
      - "PUT,DELETE /api/v1/ops/team/roles/**"          # 角色编辑/删除/改权限/改成员
      - "PUT,DELETE /api/v1/ops/team/members/**"        # 运营成员编辑
      - "POST /api/v1/ops/team/members/*/**"            # 重置密码/停启用（精确路径的新建仍放行）
      - "PUT /api/v1/ops/settings/security_policy"      # 安全策略参数禁改
      - "POST /api/v1/ops/profile/mfa/totp/**"          # 禁止给共享账号绑验证器（防绕过邮箱验证改密锁号）
```

规则建议按"能破坏数据、能抢占账号"的接口从严圈定，只读接口与常规业务演示不受影响。守卫运行在认证过滤器之前，规则由部署侧维护、随环境走，底座代码不内置任何默认黑名单。
